Closure inference works in several stages. First, we do type inference on the various blocks of code.
At this point we infer the *signature* of closures, but not necesssarily the "closure kind", i.e. whether it's an FnOnce, FnMut, or Fn.
We do collect some constraints during that phase though, which is why we're careful not to constrain the kind of the function with how `print_closure_info` is implemented.

Next, after all type inference for a function is done, we analyze upvars, i.e. captured variables, to determine the closure kind.
This is a very limited analysis, and some of the assumptions it makes are wrong. That's fine, because during borrowck, we check that whichever assumptions were made are sound.

One important fact, though, is that whether a closure is `move` means essentially nothing for what the closure kind is going to be: `move` determines whether captured variables
from the outer environment are moved *into* the implicitly generated closure struct.
The closure kind depends on whether the body of the closure then mutates or moves any of those captures *out* of the closure.

Now for the answer to the question: 

- `a` is moved out of the closure into `_a`. Hence it must be an `FnOnce`.
- `b` is also moved out of the closure, but through a `match`, still an `FnOnce.
- `c` is read in the closure (by the match), but isn't *moved* out of the closure because it's matched against the special `_` pattern. That makes it an `Fn`.
- `d` is, despite matching against `&mut _d`, only just read in the closure, not mutated, hence `Fn`.
- `e` feels a lot like `d` and `a`. However, something subtly different happens. When an assignment happens in a let, 
  and there is an "expectation", i.e. an explicitly given type hint, Rust automatically inserts a *reborrow*. This means it's an `FnMut`, not an `FnOnce` like `a`.
  This same expectation does not matter for `d`.
- `f` and `g` are equivalent, and are both an `Fn`.
- `g` captures only by reference, `println!()` inserts it automatically for you, so `Fn`.
- `i` is an `FnOnce` though, since `dbg!()` moves its input, and returns it as its output like `fn(T) -> T`

A funny quirk of how the language is implemented: the closure kind internally is stored as a type variable, so we can work with it in our inference code.
To distinguish `Fn`, `FnMut` and `FnOnce` we use the types `i8`, `i16` and `i32` (in that order) to distinguish the three kinds.
These three types just happen to be easy to name, since they're built into the language. There's no other good reason for that, 
and as a user you'll never need to be aware of this implementation detail :3
